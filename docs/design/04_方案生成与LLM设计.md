## 1. 服务总体流程

```
                ┌───────────────────────────────┐
                │  1. 上下文装配（仅取数据库字段）  │
                │  画像快照 │ 评分快照 │ 短板结论 │ 政策候选集 │
                └───────────────┬───────────────┘
                                │
                ┌───────────────▼───────────────┐
                │  2. 前置校验                    │
                │  画像 / 评分 / 短板齐备？       │
                └───────┬───────────────┬───────┘
                   齐备  │               │ 缺项 → 40010，阻止生成
                ┌───────▼───────────────┐
                │  3. 政策匹配（规则+检索）│
                │  输出候选政策及匹配维度    │
                └───────┬───────────────┘
                        │
                ┌───────▼───────────────┐
                │  4. LLM 结构化生成      │
                │  提示词模板 v1 + JSON Schema │
                └───────┬───────────────┘
                        │
            ┌───────────┼───────────┐
        成功  │           │ 结构非法    │ 失败/超时/超限
            ▼           ▼           ▼
     ┌─────────┐  ┌───────────┐  ┌──────────────┐
     │ 5. 结构校验│  │ 重试 1 次  │  │ 6. 规则模板兜底 │
     └────┬────┘  └───────────┘  └───────┬──────┘
          │ 合格                            │
          ▼                                │
     ┌───────────────────────────────────▼────┐
     │ 7. 落库：方案草稿 + 版本 + 留痕（模型/模板/耗时/token）│
     └────────────────────────────────────────┘
```

关键约束：

- 进入 LLM 的事实字段全部来自数据库，提示词里明确要求模型不得编造企业数据、政策条款和数字。
- LLM 必须返回约定的 JSON 结构；校验失败不写入正文，转重试或兜底。
- 任何生成结果（含兜底模板）都先存为草稿，经规划人员核验后才能定稿（REQ-PLAN-07）。

## 2. 上下文装配

| 上下文块 | 来源 | 字段 | 用途 |
| --- | --- | --- | --- |
| 短板结论 | D1 | 环节、缺口类型、缺口描述、优先级 | 说明"为什么招这家企业补这个缺口" |
| 筛选命中原因 | D2 | 命中条件、命中原因 | 推介要点中的匹配依据 |
| 企业画像 | D3 | 6 维画像字段及来源 | 企业事实素材 |
| 评分结果 | D4 | 总分、维度分、评分理由、风险提示 | 方案中的优势表述与风险提示口径 |
| 政策候选集 | 政策库 | 政策条目、标签、条款、来源 | 政策包匹配与引用 |

装配时生成上下文快照 ID（`profile_snapshot_id` / `score_snapshot_id`），方案定稿后引用快照，避免上游数据改动后已定稿方案跟着变。

## 3. 提示词模板设计

### 3.1 模板结构（`TPL-ONE-COMPANY-v1`）

```text
# 角色
你是某地产业链招商专班的方案撰写助手。你只能依据下方【给定资料】组织语言，
不得引入资料以外的企业事实、数据、政策名称或条款。

# 任务
围绕【短板环节】与候选企业，撰写一份"一企一策"招商方案，包含：
1. 推介要点 highlights：企业优势与本地补链方向的契合点；
2. 匹配政策 matched_policies：仅从【政策候选集】中选取，注明匹配维度与理由；
3. 谈判策略 negotiation_points：对接切入要点、对方关切、我方筹码；
4. 分步行动计划 action_steps：分阶段动作、责任建议、时间建议。

# 给定资料
- 短板结论：{shortboard}
- 命中原因：{hit_reason}
- 企业画像：{profile}
- 评分与理由：{score}
- 风险提示：{risk_note}
- 政策候选集：{policies}

# 输出要求
- 严格输出 JSON，字段与下述 Schema 一致，不要输出 JSON 以外的解释文字；
- 企业名称、规模、技术资质、投资动向等事实必须与【给定资料】一致；
- 政策只能引用候选集中的 policy_id，不得虚构；
- 风险提示不得隐瞒，需在推介要点或谈判策略中如实体现；
- 语言简洁，面向专班内部评审，不做对外宣传口径。

# 输出 JSON Schema
{
  "highlights": ["string"],
  "matched_policies": [
    { "policy_id": 0, "match_dimension": "string", "match_reason": "string" }
  ],
  "negotiation_points": ["string"],
  "action_steps": [
    { "stage": "string", "actions": ["string"], "owner_suggest": "string", "timeline": "string" }
  ]
}
```

### 3.2 模板管理

- 模板按 `template_id` 版本化存储；生成记录引用模板版本。
- 变更模板需登记：修改人、修改原因、影响字段；旧模板保留可回溯。
- 演示期可准备两套模板：`TPL-ONE-COMPANY-v1`（一企一策标准版）、`TPL-FOLLOW-UP-v1`（跟进洽谈版，用于重新生成）。

### 3.3 幻觉抑制措施

1. 事实字段由服务端拼接进上下文，模型不负责"回忆"企业信息；
2. 输出政策必须挂接候选集内 `policy_id`，服务端二次校验 ID 合法性；
3. 方案正文中的数字（投资额、人数、专利数等）回查画像快照，不一致即驳回本次生成；
4. 生成结果与来源字段在页面上并列展示，便于人工核对（REQ-PLAN-03、NFR-03）。

## 4. 政策匹配设计

### 4.1 两级匹配

**第一级：规则召回（可解释、可兜底）**

- 正常路径调用数据岗 C2 政策匹配接口（按企业或行业＋地域召回，返回 `match_reasons`），本岗沿用其命中理由并归纳命中维度；
- C2 不可用时启用本岗本地规则兜底：行业名称、产业链环节、地域、资质关键词做等值 / 包含匹配；
- 命中记录 `match_dimension`（行业环节 / 地域布局 / 要素资质）。

**第二级：语义检索（RAG，本期可选增强）**

- 政策条款经 Embedding 入库；以企业画像摘要 ＋ 短板环节为query 召回 Top-K；
- 与规则结果合并去重，按规则命中权重 ＋ 检索相似度排序；
- 每条结果保留 `match_reason`（命中的标签或相似条款依据）与 `source`。

### 4.2 匹配输出字段

| 字段 | 说明 |
| --- | --- |
| policy_id | 政策库记录 ID（整数），服务端校验存在性且来自 C2 候选集 |
| name / clause | 政策名称与条款原文（取自政策库，不改写） |
| match_dimension | 命中维度：行业环节 / 要素 / 规模 / 资质 / 语义相似 |
| match_reason | 为什么匹配该企业，引用具体标签或条款 |
| source | 政策文件来源 |

### 4.3 边界处理

- 无命中：政策包返回空列表，方案中注明"暂未匹配到适用政策"，不虚构条目；
- 检索服务失败：仅保留规则召回结果并标注"语义检索暂不可用"；
- 政策过期 / 失效：政策库标记状态，匹配时过滤。

## 5. 兜底模板生成（LLM 不可用时）

触发条件：LLM 超时、限流、余额不足、返回结构连续两次非法。

兜底规则模板按固定段落拼装，素材全部取自数据库字段：

1. **推介要点**：由画像标签 ＋ 评分理由 ＋ 命中原因拼接；
2. **政策包**：直接挂接规则匹配结果；
3. **谈判策略**：按风险提示与要素匹配生成固定条目（如"回应用工 / 用地 / 用电关切"）；
4. **行动计划**：按"对接准备 → 上门对接 → 落地跟进"三阶段生成默认步骤。

兜底结果 `generator=template`，页面与台账明确标注"模板生成"；不冒充 LLM 产出，同样进入人工核验。

## 6. 留痕与可追溯

每次生成 / 重新生成记录：

| 留痕项 | 内容 |
| --- | --- |
| 上下文快照 | 画像快照 ID、评分快照 ID、短板 ID、政策候选集版本 |
| 生成方式 | `llm` / `template`；模型标识与版本；模板 ID 与版本 |
| 运行信息 | 耗时、token 用量（可取时）、失败原因 / 降级原因 |
| 核验记录 | 核验人、时间、动作（定稿 / 驳回）、意见 |
| 版本 | 版本号、旧版本归档状态 |

对应风险预案：

- **R1 LLM 不可用 / 超限 / 超预算**：模板兜底 ＋ 结果缓存 ＋ 用量监控与阈值告警；
- **R6 生成内容失实**：数据只取数据库、模型仅组织语言、定稿前人工核验、条目可回溯来源。

## 7. 后端骨架说明

`backend/` 目录提供可直接并入 FastAPI 工程的骨架：

| 文件 | 内容 |
| --- | --- |
| `schemas.py` | Pydantic 模型：画像、评分、政策、方案请求 / 响应、状态枚举 |
| `policy_matcher.py` | 规则匹配 ＋ 检索结果合并排序的骨架 |
| `plan_service.py` | 上下文装配 → 校验 → 生成（LLM 接口预留）→ 兜底 → 落库留痕 |
| `api_routes.py` | FastAPI 路由骨架，路径与《03_接口契约》对应 |

> LLM 客户端在骨架中以 `call_llm()` 抽象方法预留；接入真实 API Key 时只替换该方法实现，其余校验、兜底与留痕逻辑不变。
